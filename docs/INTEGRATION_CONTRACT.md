## 1. Architecture & Execution Model

The PRECURSOR backend engines and Streamlit dashboard reside within the same repository and Python runtime environment. 

To achieve maximum throughput, sub-millisecond reaction times, and zero inter-process overhead, the dashboard directly instantiates and orchestrates **`PrecursorEngine`** in memory:

```python
from precursor.runner import PrecursorEngine, SystemSnapshot
from precursor.telemetry.synthetic import ScenarioType
from precursor.telemetry.schema import MetricBatch, TelemetryPoint
```

## 2. Session Lifecycle in Streamlit (`dashboard/app.py`)

### 2.1 Initialization
On dashboard initial load, initialize `st.session_state.engine` with the selected scenario and seed an initial 25 steps (125 seconds) of nominal baseline:

```python
if "engine" not in st.session_state:
    st.session_state.engine = PrecursorEngine(
        scenario_type=ScenarioType.GRADUAL_DEGRADATION,
        seed=42,
        interface_id="eth0"
    )
    # Pre-seed nominal 25 steps (125s) so charts immediately show baseline
    st.session_state.snapshot = st.session_state.engine.fast_forward(125.0)
    st.session_state.current_scenario = ScenarioType.GRADUAL_DEGRADATION.value
```

### 2.2 Scenario Switching & Reset
When the operator selects a new synthetic scenario from the sidebar:

```python
if st.session_state.current_scenario != selected_type.value:
    st.session_state.current_scenario = selected_type.value
    st.session_state.engine.reset_scenario(selected_type, seed=42)
    st.session_state.snapshot = st.session_state.engine.fast_forward(125.0)
    st.rerun()
```

### 2.3 Time-Travel Controls
- **Step +5s**: Advances the synthetic timeline by exactly one 5-second interval:
  ```python
  st.session_state.snapshot = st.session_state.engine.step_simulation()
  st.rerun()
  ```
- **Jump +1m**: Advances the timeline by 60 seconds (12 steps):
  ```python
  st.session_state.snapshot = st.session_state.engine.fast_forward(60.0)
  st.rerun()
  ```
- **Reset**: Re-initializes the scenario generator and clears the ring buffer:
  ```python
  st.session_state.engine.reset_scenario(selected_type, seed=42)
  st.session_state.snapshot = st.session_state.engine.fast_forward(125.0)
  st.rerun()
  ```

### 2.4 Live Linux Telemetry Ingestion
When operating in live telemetry mode:

```python
live_batch = st.session_state.collector.collect()
st.session_state.snapshot = st.session_state.engine.ingest_points(live_batch.points)
```

## 3. Data Structures & Contract Specification

All dashboard components receive structured data from `SystemSnapshot`:

### 3.1 `SystemSnapshot` Object
```python
snapshot.timestamp: float                          # UTC epoch seconds
snapshot.latest_telemetry: Dict[str, Optional[float]] # Latest metric readings
snapshot.quality_stats: Dict[str, Any]             # good_ratio, missing_ratio, stale_ratio
snapshot.gate_decision: GateDecision               # Reliability state & audit reasons
snapshot.detector_results: Dict[int, List[DetectorResult]] # Multi-horizon detector outputs
snapshot.incidents: List[Incident]                 # Active faults and predicted incidents
snapshot.copilot_response: Optional[CopilotResponse] # Grounded LLM runbook guidance & verified claims
```

### 3.2 Reliability Gate State (`GateDecision`)
The 3-state machine regulates multi-horizon predictive alerts:
- **`PREDICT`**: All sensors nominal, distribution matches baseline, model variance bounded.
- **`DEGRADED`**: Statistical drift detected ($KS > 0.30$) or residual variance expanded ($> 2.5\times$ baseline). Alerts flagged with reduced confidence.
- **`ABSTAIN`**: Sensor corruption ($> 40\%$ missing/stale). Suppresses predictive warnings to prevent false alarm fatigue.

> [!IMPORTANT]
> **Safety Invariant:** `gate_decision.immediate_alerts_active` is **ALWAYS `True`** in all three states. Physical interface drops and 100% loss are never suppressed by gate abstention.

### 3.3 Incidents & Disambiguation (`Incident`)
Incidents deterministically cluster co-occurring signals:
- **Active Faults**: `incident.is_active_fault == True`, `incident.predicted_horizon == None`. Represents current physical or protocol outages (e.g., link down, 100% loss).
- **Early Warnings**: `incident.is_active_fault == False`, `incident.predicted_horizon in (5, 15, 30)`. Represents developing pre-impact degradation.

### 3.4 Numerical Claim Verification (`ClaimVerification`)
Claims generated by the LLM or heuristic engine are validated against rolling telemetry:
- **`VERIFIED`**: Claimed numeric value matches rolling observation within $\pm 10\%$.
- **`CONTRADICTED`**: Claimed value conflicts with actual observed telemetry (guarding against hallucinations).
- **`UNVERIFIED`**: Claim refers to metrics absent from the ingested telemetry batch.

### 3.5 Paired Benchmark Evaluation (`ScenarioComparisonResult`)
Tab 3 executes head-to-head comparison on identical scenario seeds:
```python
comparison = st.session_state.engine.run_paired_evaluation(selected_type, seed=42)
```
Evaluates metrics by horizon (5m, 15m, 30m) for **GATE ON** vs **GATE OFF**:
- **Event Recall** ($0.0 - 1.0$)
- **False Alarms / Hour** (Alert fatigue reduction)
- **Warning Lead Time** (Minutes prior to SLA breach)
- **Missed Faults** (Must remain zero)
- **Abstention Rate** (Percentage of corrupted windows abstained)

## 4. Error Handling & Fallbacks

1. **Ollama Offline**: When local Ollama (`http://localhost:11434`) is unreachable or times out ($> 6.0\text{s}$), the Copilot automatically switches to `offline_heuristic_fallback`. Markdown runbook guidance and numerical claim verification remain 100% functional.
2. **Missing / Stale Telemetry**: Missing samples are tagged with `MetricQuality.MISSING` or `STALE` and trigger gate degradation or abstention with audit trails.
3. **Execution Platform**: Compatible with rootless Podman execution via `systemd-run` and the cached `nix develop` devshell.
